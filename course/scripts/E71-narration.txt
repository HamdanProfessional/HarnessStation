# Slide 1
Module 19 is testing and contributing. Before touching a single line, know how to prove nothing broke — the same two commands the project's own CI runs on every push.

# Slide 2
npm test runs Vitest over the tests folder. Hundreds of specs, covering the pure logic across the codebase plus the sharper stuff: the store's streaming path, the tool-call loop, the lazy chat-hydration invariants, the agent loop, the memory store, the voice stack. This is the same command E04 had you run right after building from source, back in Module 1 — now you're seeing what it's actually protecting.

# Slide 3
npx tsc --noEmit is the second half — no test runs, it just type-checks the whole project. This is what catches a shim whose signature drifted from the real Tauri import, or a component destructuring a store action that got renamed. Clean output, no errors, is success — silence is the passing state.

# Slide 4
Both of these, plus a Vite build and cargo clippy and cargo test on the Rust side, run automatically in ci.yml on every push and every pull request. Nothing merges without all four passing — so running them locally first is just doing on your machine what would otherwise fail in public a few minutes later.

# Slide 5
Now the Rust side of testing, as a concrete example, revisiting E51. start_server has a real side effect — it spawns a process — so it can't be unit-tested directly without actually launching llama-server. The fix: launch_flag_args, the part that turns LaunchOpts into a Vec of command-line strings, was pulled out as its own pure function. No side effects, so it's trivial to test in isolation.

# Slide 6
And the test itself checks the exact compatibility guarantee from E51: a default LaunchOpts, with nothing set, must produce an empty Vec — no flags at all. That's what lets an older llama-server binary that's never heard of --n-cpu-moe or --fit-target still launch cleanly. One assertion, no process, no server, and it runs in milliseconds as part of cargo test.

# Slide 7
The pattern generalizes past this one file. Anything with a side effect — spawning a process, hitting the network, touching a real filesystem — resists testing directly. The fix is almost always the same: pull the decision-making part out as a pure function of its inputs, test that thoroughly, and keep the side effect itself as a thin, un-tested wrapper around it.

# Slide 8
With the checks understood, next episode is your first real contribution — adding a genuine built-in tool to the codebase, the way a real pull request would, rather than a user-authored script.
