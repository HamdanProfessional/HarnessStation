# Slide 1
This one's genuinely advanced and code-literate: the actual llama-server flags the app can pass, what each does, and why they're safe to leave alone if you never touch this screen.

# Slide 2
Every flag on this screen is opt-in. Leave a field unset and nothing is emitted for it on the command line — the server just uses its own defaults. That single rule is what lets an older llama-server build launch cleanly even with a newer app version pointed at it.

# Slide 3
Threads sets CPU thread count — best set near your physical core count, not your logical thread count. Flash attention is close to a free win almost everywhere, so turn it on. Mlock pins the model in RAM so it can't be swapped to disk; no-mmap loads it fully into RAM up front instead of memory-mapping it lazily.

# Slide 4
The one worth knowing by heart: MoE offload. Cpu-moe pushes every expert layer of a mixture-of-experts model onto system RAM; n-cpu-moe N pushes just the first N. Attention stays on the GPU, the experts sit in RAM — that's the trick for running a big MoE model on a small GPU that could never hold the whole thing.

# Slide 5
Llama.cpp auto-fits itself to your hardware by default. Fit off turns that auto-fit off entirely if you want manual control, and fit-target sets the memory margin in megabytes it leaves free per GPU when auto-fit is on.

# Slide 6
This isn't just a claim — the launch_tests module in local.rs unit-tests exactly this: an empty options struct produces an empty argument list, and each flag appears only when its field is set. That's the opt-in design, proven in code.

# Slide 7
The gotcha: these flags only take effect on an engine new enough to know them. If you set a flag and see no difference, the first thing to check isn't your settings — it's the llama-server build version.
