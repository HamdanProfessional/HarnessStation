# Slide 1
There's a real cost difference between putting something in your global instructions, which you pay for on every single message, and putting it in a skill, which you only pay for when it's actually relevant. This episode is about skills.

# Slide 2
Automation, Skills, New skill. Three fields: a name, a one-line description, and a Markdown body with the actual procedure. The description is the part the model always sees; the body only loads in when the description matches what's being asked.

# Slide 3
The worked example: a sql-conventions skill. Its body holds your team's actual rules — table naming, migration format, how to write a safe query. It sits there unused in every unrelated chat, and loads in fully the moment someone asks for a query or a schema change.

# Slide 4
The one rule that makes or breaks a skill: the description must say when to use it, not what's inside it. Contains our SQL style guide tells the model nothing about which moment to reach for it. Use this when writing or reviewing any SQL query or migration is specific enough to trigger reliably.

# Slide 5
Three ways to hold information, and they're not interchangeable. A skill is a procedure, loaded in whole when relevant. Knowledge is large material, searched piece by piece at question time. Memory is small facts about you or the project, injected into every single message whether it's needed or not.

# Slide 6
And memory, the third kind: small facts, always injected, on every single message — the most expensive place to put anything long.
